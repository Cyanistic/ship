# Ship website

The landing page and versioned docs for Ship. `PRODUCT.md` is the brief: it is the authority on who the site serves, its voice, what it may claim, motion and accessibility.

## The look

The ansi direction in `directions/ansi/` is the approved look, and the site is a port of it. When the site and ansi disagree, the site is wrong. `directions/` is a frozen reference: read from it, copy out of it, and leave it as it is, until a DESIGN.md replaces it as the design record.

The art and marks are generated by the scripts in `directions/ansi/tools/`, and the SVGs under `public/` are copies of their output. To change art, change the generator and copy the result across.

Art added since the freeze is generated by `tools/art.py` straight into `public/art/`. Change the script and run it with `python3 tools/art.py`; don't edit the SVG.

## Docs sources

`docs/site/` holds the real docs, and people read them on GitHub as much as on the site. Keep them plain GitHub markdown in sentence case, with relative links between pages, so they stand on their own without the site. Anything that exists only for the site, such as lowercase display, the crewmate notes or the version banners, belongs in the site's build and styles, with the sources left untouched.

## Base path

The site can be served under a path (`SHIP_BASE`, `/ship/` on GitHub Pages) as well as at the root. Write site-relative paths like `/docs/` and `/css/site.css` in code, and send every one that reaches the browser through `withBase()` from `src/base.ts`, or `rebase()` for raw HTML. A bare `/` link works at the root and breaks under a base, and the build will not catch it. Markdown links in `docs/site` are rebased by `src/markdown/links.mjs`, so leave them site-relative.

## Agent-facing files

`agent-guide.md`, `llms.txt` and the raw `.md` copies are a public interface, read by agents on other people's machines. Treat changes to them like changes to Ship's CLI. Keep what they ask of an agent to installing, configuring and using Ship.

## Compactness

The root rule applies here too: own the content and the look, rent the mechanisms. Reach for what Astro and Starlight already provide before writing a mechanism, and override a Starlight component only when the ansi look needs it.
